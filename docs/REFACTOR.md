# 도메인 모델 리팩토링

## 멘탈 모델

### 현실의 로또 — 등장하는 것들

```text
사물 (Object)
  - 로또 번호(공) — 1~45 중 하나
  - 로또 티켓 — 6개 번호가 적힌 종이 한 장
  - 구매 금액 — 내가 낸 돈
  - 추첨 결과 — 당첨 번호 6개 + 보너스 번호 1개 (하나의 덩어리)
  - 등수 — 1등~5등 또는 꽝

행위자 (Actor)
  - 나 (구매자)
  - 판매점/로또기계 — 돈 받고 티켓 발행
  - 추첨 방송 — 당첨 번호 발표
```

### 현실의 흐름

```text
[나]  ──돈을 낸다──▶  [판매점]  ──발행한다──▶  [로또 티켓 여러 장]
                                                    │
[추첨 방송]  ──발표한다──▶  [추첨 결과]                 │
                              │                      │
                              ▼                      ▼
                         ┌─────────────────────────────┐
                         │      대조한다 (비교)          │
                         │  추첨 결과 × 각 티켓 → 등수   │
                         └──────────┬──────────────────┘
                                    ▼
                              [등수 목록]
                                    │
                                    ▼
                              ┌───────────┐
                              │  집계한다   │
                              │ 통계, 수익률 │
                              └───────────┘
```

### 핵심 관찰

1. **"추첨 결과"는 하나의 덩어리** — 6개 번호 + 보너스를 따로 발표하지 않음
2. **"발행"은 판매점의 행위** — 티켓 묶음이 스스로 자신을 발행하지 않음
3. **"대조"와 "집계"는 나의 행위** — 티켓이 스스로 대조하지 않음
4. **"나"는 행위의 주체이지 데이터 객체가 아님** — 오케스트레이터(LottoGame)가 "나"

## Phase 1: OOP 내에서 멘탈 모델 바로잡기

### 문제 1. Rank의 멘탈 모델이 구조에 의해 왜곡되어 있다

Rank의 본질은 "등수 + 상금"이다. 그런데 판정 조건인 matchCount와 isBonusMatch까지 Rank의 인스턴스 속성으로 구겨넣다 보니, `NONE = new Rank(2, false, 0)`처럼 거짓말을 하거나 `FIRST`의 `isBonusMatch: false`처럼 의미 없는 값을 채워야 한다. 또한 이 값들은 뷰에서 "3개 일치" 같은 텍스트를 렌더링하기 위해 존재하는 것이므로, Rank가 도메인 책임이 아닌 뷰 책임까지 갖고 있는 상태다.

**해결**: Rank에서 판정 조건을 제거하고 prize만 남긴다. 뷰 표시 책임은 뷰 레이어로 분리한다.

- Rank 생성자를 `constructor(prize)`로 단순화
- `from(matchCount, isBonusMatch)` switch 판정 로직은 유지 (입력값으로만 사용, 저장하지 않음)
- RankStatistics.summary는 Rank 인스턴스를 직접 포함하도록 변경
- matchCount/isBonusMatch 표시 데이터는 뷰 레이어가 직접 관리
